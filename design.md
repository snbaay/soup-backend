# Design note — training-job queue

**Scope.** Python/FastAPI, SQLAlchemy/psycopg, PostgreSQL, pytest, Docker Compose; `docker compose up` starts API and four workers (eight in chaos). Simulated work has one durable database effect. PostgreSQL is the sole queue store; an outage pauses service. No broker. All queue transactions use `READ COMMITTED`, are short, and roll back on errors.

**Rows and API.** `jobs`: UUID, unique non-null idempotency key, canonical request hash, status (`queued|running|succeeded|failed|cancelled`), attempts, lease generation/owner/expiry, hard attempt deadline, timestamps and error. `execution_effects`: primary-key `job_id` FK, payload and timestamp. Create, get, paginated list and cancel endpoints. A concurrent same-key insert conflict reads the winner: same hash returns its job, different hash returns HTTP 409. The hash uses normalized request fields; list order is (`created_at,id`). Keys are global with no expiry or retention policy yet. A lost create response is safe to retry by key.

**Claim and recovery.** One short transaction locks an eligible `queued` or lease-expired `running` row with `FOR UPDATE SKIP LOCKED`, rechecks eligibility, increments attempts and fencing generation, assigns owner and database-time lease/deadline, then commits before work. Claims exclude exhausted attempts (limit: 3). A periodic recovery pass marks expired, exhausted `running` jobs `failed`; other expired jobs are claimable. A hard attempt deadline bounds hung work even if heartbeats continue. Recovery also runs when no new jobs arrive. Progress requires a live worker and restored database.

**Lease and fencing.** Lease, heartbeat, deadline and completion use PostgreSQL `clock_timestamp()`, never worker clocks. Heartbeats and all worker writes require `running`, matching owner/generation, and unexpired lease/deadline. Heartbeat extends only to `min(database_time + lease_duration, attempt_deadline)`. An expired worker loses authority even before reclaim; retry advances the generation. Work holds no database lock. A rejected heartbeat asks the worker to stop; stale writes remain fenced regardless.

**Cancellation and completion.** Cancel locks the row and changes `queued`/`running` to terminal `cancelled`, clearing ownership. Terminal jobs return their existing state. Completion locks the same row; only a current, unexpired owner inserts `job_effects` and sets `succeeded` **in one transaction**. Owned work failure queues a retry or fails at the limit. The first committed cancel/complete transaction wins: cancel first forbids an effect; completion first leaves `succeeded`. Terminal states never change; failed/cancelled jobs have no effect.

**Guarantee and evidence.** Eligible work may execute repeatedly, up to three attempts; cancellation may prevent it. `UNIQUE(job_id)` and atomic completion ensure **at most one committed database effect**, exactly one for `succeeded`; execution and external API effects are not exactly once. Tests cover idempotency conflicts, double claims, cancel/complete order, lease expiry, zombie writes, hard deadline, attempt exhaustion, clock skew, SIGKILL and restart using separate `READ COMMITTED` connections. The host chaos harness targets 10,000 keys, eight workers, SIGKILL about every 2s, concurrent retries/cancels, seeded/timestamped logs, replacements, and recovery. Each run retains raw logs in `artifacts/runs/`. SQL plus expected-key reconciliation checks no duplicate effects, no missing keys, no `queued`/`running` after recovery, and `succeeded` iff one effect. The harness has not run here because PostgreSQL/Docker are unavailable. A 100 RPS submission target is not capacity evidence. Finite tests miss some schedules, partitions, host/database crashes, prolonged outages and external effects. **DON'T SHIP at 100 RPS** until integration, chaos, and representative load runs complete.
